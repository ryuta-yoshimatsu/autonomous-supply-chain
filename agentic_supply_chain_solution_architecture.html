Solution Architecture — As Built

The end-to-end Databricks solution as it runs today: read-only SAP-style source facts in gold_opus5 feed a forecast, five digital twins, a governed relationship + KPI layer, a cross-twin events inbox, and two planning engines (inventory policy + time-phased MRP) — all in the monitoring schema and consumed by an AI/BI control tower, Genie, and the Twin Explorer app. The plan-of-record store and governed agent close the loop next.

Closed loop

Committed actions in Respond feed back into Plan; the next refresh re-measures the twins against the committed plan and raises new events on drift.

3Layer Details

What each layer does, how it is built, and the design choices behind it.

Source — gold_opus5 read-only

SAP S/4HANA-style gold layer for one roastery & café (plant 1000, Oxford Street) selling through counter sales (ZPOS), wholesale (ZOR) and delivery-app orders (ZDEL).

  • Batch snapshot to 2026-08-04; no live feed.
  • Only ZOR orders are shipped and netted against deliveries (99.3% coverage).
  • Upstream demandplan is ignored — our forecast lives in monitoring.

Foundation & config nb 00 · 01 · 03

Creates the derived schema, profiles every source role before any modelling, and seeds the single registry of business/policy parameters.

  • planning_config: service level, review period, MOQ, holding / ordering cost, detection thresholds.
  • Resolution: most-specific scope wins (MATERIAL > MATERIAL_GROUP > PLANT > GLOBAL).
  • Data-derived params (lead time, demand stats) stay in the twins.

Forecast nb 02

Per material × plant × channel weekly forecast from sales history with statsforecast AutoETS (seasonal-naive moving-average fallback for short series).

  • Versioned: each run demotes the previous IsCurrentVersion and appends.
  • Rolling-origin backtest → demand_forecast_accuracy (WMAPE, bias, PI coverage).
  • Cumulative h-step errors → demand_forecast_error_sets for conformal safety stock.

Digital twins nb 04–08

The canonical state layer. Every KPI, event, engine, app and agent reads from these — never from raw source tables.

  • One *_twin_current (latest state, last-365-day window) and one *_twin_metrics_timeseries (full history) per twin.
  • Column comments re-applied on every overwrite so the catalog stays documented.
  • Thresholds come from planning_config via cfg(key, default).

Relationship & semantic layer nb 09 · 10

Views first: the twins become one typed graph, and every KPI has exactly one governed definition.

  • Nodes coloured GREEN / AMBER / RED by twin status; 7 edge types.
  • v_material_bom_edges preserves qty / scrap / UoM for MRP.
  • Metric views separate dimensions from measures (MEASURE()).

Detect — events nb 13

A thin, deterministic detection layer: one shared inbox across all twins instead of five event models.

  • Types: stockout / low cover / overstock, supplier risk, bottleneck / low yield, fulfillment risk, forecast drift.
  • Each row: entity, metric vs threshold, severity, owner, source table, recommended_action.
  • Mutable status / ownership moves to Lakebase later.

Plan — inventory policy nb 14

Distribution-free order-up-to policy for independent-demand items: S* = μX + SS, with SS the split-conformal quantile of cumulative P-step forecast errors.

  • replenishment_mode: PO (supplier lead time), PRODUCTION (production lead time), MRP_DEPENDENT (handed to MRP).
  • Writes quantified actions onto open inventory events.

Plan — MRP nb 15

Time-phased weekly MRP over 13 weeks that re-applies nb 14's lead-time-sized policy week by week, then explodes planned production through the BOM.

  • Low-level coded: parents before components; components get gross requirements from parent releases.
  • Week 1 equals nb 14's "order now?" decision by construction.
  • Outputs projected on-hand, planned receipts and lead-time-offset releases.

Control tower nb 11 · 12 · app

Three ways in, all on the same governed tables and the same SQL warehouse.

  • AI/BI dashboard — executive + per-twin pages.
  • Genie — natural-language questions over twins and metric views.
  • Twin Explorer — Streamlit app with per-twin filters, time-series drilldowns and the material-centric network graph; queries run as the signed-in user so UC permissions apply.

5What Is Not Built Yet

The remaining work, split between components to build and data the source does not yet provide.

Components to build planned

  • Plan-of-record & scenario store — Lakebase (Postgres) with a Delta mirror; versioned plans, approvals, rollback.
  • Governed agent — UC-function tools (diagnose, simulate, draft actions), every call logged, human approval before commit.
  • Finite-capacity scheduler — setup-matrix changeovers + OR-Tools sequencing on ROASTER / PACKING.
  • Distribution & freight-lane optimizer — carrier / lane selection over the rated lane offers.
  • SQL Alerts / anomaly jobs — route events to owners; schedule the refresh as a recurring job.

Source data gaps data

  • Outlet / DC network — one plant only; the 40 transport destinations are wholesale customers, so the network is single-echelon.
  • Open production orders — none at the snapshot, so WIP and work backlog read 0.
  • Live feed — batch snapshot to 2026-08-04, about three months behind.
Guardrails built into the design: source stays read-only; agents get narrow governed tools rather than table access; every recommendation cites the KPI deviation, impacted entities, root cause, scenario comparison and expected impact; and if data is stale, policies are missing or a solver fails, the agent stops at diagnosis and escalates instead of acting.
