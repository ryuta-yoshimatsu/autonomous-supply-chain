Implementation Plan: Digital Twin-First Agentic Orchestration

Build a robust agentic supply chain platform on mickmickstableawscoff_catalog.gold_opus5 (snapshot to 2026-08-04) by first creating near-real-time digital twins of the network, then layering KPIs, alerts, planning engines, plan-of-record, and governed agents on top.

Recommendation

The digital twin-first approach is the right foundation. Do not build dashboards, alerts, or agents directly on raw SAP-style gold tables. First build business-state twins, then let every downstream capability read from those stable state models.

1Target Architecture

A layered architecture that keeps source facts, state, planning, monitoring, and agentic actions separate.

Source
Gold tables (gold_opus5, read-only): sales, vendor performance, inventory ledger / snapshots, production orders, confirmations, BOM, routings, setup matrix, work centres, outbound deliveries, shipments / transport requirements / freight lanes, billing. Its upstream demandplan is not used; our forecast is written to monitoring.demandplan.
v
State builders
Scheduled near-real-time jobs / pipelines: generate / refresh demand forecast first, normalize source facts, validate freshness, run data quality checks, and materialize digital twin state tables.
v
Digital twins
Demand, procurement, inventory, production, and distribution twins: the canonical current-state and time-series representation of the supply chain.
v
Monitor
Control tower: digital twin views, KPI time series, AI/BI dashboards, Genie, alerts, anomaly detection, and event tables — including an interactive twin-network graph (interconnected supplier / material / plant / work-centre / customer nodes) where users click a node to drill into its operational data. Users should be able to inspect the live state of each twin, not only summary KPIs.
v
Plan
Planning engines: inventory policy, MRP, finite production scheduling, distribution planning, scenarios, and optimization. Consume the twins and monitored events (e.g. the inventory-policy engine turns detected stock abnormalities into replenishment recommendations).
v
Respond
Agentic orchestration: agents diagnose, explain, run scenarios, recommend actions, request approval, and trigger approved workflows.

2Digital Twins to Build First

These twins are the system's state layer. Every KPI, alert, optimizer, app, and agent should read from them.

Demand / Customer Twin

This twin represents what customers are asking for now and what they are expected to ask for next. It combines firm demand from sales orders with the forward-looking demand forecast generated by notebook 02 into monitoring.demandplan, so forecast generation must run before this twin is fully hydrated.

It should capture open demand, backlog, forecast demand, actual-vs-forecast error, demand volatility, and customer/product context. Downstream, it drives inventory targets, MRP net requirements, production priorities, and distribution plans.

Procurement Twin

This twin represents the inbound supply network: which suppliers are expected to deliver which materials, when they are expected to arrive, and how reliable each supplier has been historically.

It should track open and past-due purchase orders, expected receipts, supplier OTIF, in-full rate, lead-time variability, rejected quantities, invoice accuracy, and supplier/material risk. It feeds MRP, stockout-risk analysis, supplier alerts, and agent recommendations like expediting or switching suppliers.

Metric option: supplier reliability rates (OTIF, on-time, in-full) are computed line-level by default; a quantity-weighted variant — weighting each PO line by its quantity so large orders count more — is an optional extension.

Inventory / Material Flow Twin

This twin is the connective tissue of the supply chain. It represents what stock exists, where it sits, how it has moved, and how long it will last under current and forecast demand.

It should combine snapshots, opening balances, and the inventory ledger to expose on-hand inventory, available-to-promise, consumption velocity, days of cover, stockout risk, overstock risk, and projected future balances. It is the core input to inventory optimization and MRP netting.

Production Twin

This twin represents the manufacturing network: what is planned, what is currently in progress, what has been produced, and where capacity or quality constraints are emerging.

It should capture open production orders, WIP, planned vs actual quantities, yield, scrap, rework, cost variance, work-centre load, bottleneck pressure, and component consumption. The routing master is now integrated (routed work content, work-backlog days as a capacity-pressure signal); for true finite scheduling it still needs a changeover model over setupmatrix and a scheduling engine. The current snapshot has no open production orders, so WIP and work backlog read 0.

Method notes / caveats: quality percents (yield_pct, scrap_pct, first_pass_yield_pct) are unweighted item-level averages — a quantity-weighted variant is an optional extension. Header metrics (cost variance, schedule adherence, on-time start, lead-time hours) are averaged across items, so multi-item orders weight more (exact for single-item orders, the norm here). open_order_count flags an order open if any item is undelivered, and open_production_qty sums OpenQuantity only on undelivered items (the planned-vs-received residual on closed orders is not open work); primary_work_centre now comes from the routings master (header fallback), with work_backlog_days (open work content ÷ effective daily capacity) as an informational capacity-pressure metric; is_bottleneck stays the OR of the master-data IsBottleneckFlag. Lead-time figures are recorded actuals from the order header, not a full scheduling model. Facts are filtered to production orders (AUTYP='10', not-deleted); current = last 365 days by production date, time-series = full history; as_of_date is the global max production date (not per-series).

Distribution / Fulfillment Twin

This twin represents the customer-facing fulfillment network: which orders are being delivered, which customers are at risk, and how well the network is meeting promised delivery dates and quantities.

It should capture outbound deliveries, delivered vs ordered quantity, delivery delay, fill rate, OTIF risk, billing linkage, and customer fulfillment status. Shipments & transport requirements are now integrated (actual vs planned transit, freight cost, window feasibility, service lateness, transport-risk flag), and the source now carries 720 rated freight lanes to 40 wholesale destinations; to become a full distribution twin it still needs freight-lane optimization and an outlet / distribution-node network.

Method notes / caveats: fill_rate is quantity-weighted, but on_time_rate / in_full_rate / otif_rate / partial_rate are line-level averages (a quantity-weighted variant is an optional extension). otif_rate treats a NULL on-time as not on-time (COALESCE(...,false)), whereas on_time_rate excludes NULLs — so OTIF can read lower. Transit now reports both avg_planned_transit_days (transport requirements) and avg_actual_transit_days (assigned shipments), alongside the older DerivedTransitDays estimate. Date basis differs by table: current is windowed by delivery creation date (last 365 days), the time-series buckets by actual goods-issue date. open_delivery_qty counts only not-yet-goods-issued lines. Deliveries cover 99.3% of shipped (wholesale ZOR) order lines; counter sales and delivery-app orders are fulfilled without a tracked delivery and are out of scope for this twin.

3Implementation Phases

Build in layers so each phase creates useful assets without forcing downstream redesign.

0Foundation

Set up the derived schema, data contracts, quality checks, naming conventions, deployment pattern, and the first demand-forecast generation job.

  • Create mickmickstableawscoff_catalog.monitoring.
  • Keep gold_opus5 read-only; derived state goes to monitoring.
  • Generate the demand forecast into monitoring.demandplan (the upstream gold_opus5.demandplan is left untouched).
  • Define freshness checks and failure behavior.

1Digital twin state layer

Materialize separate current-state and time-series Delta tables for the five business-domain twins.

  • After demand forecast is populated, build demand and inventory first, then procurement, production, distribution.
  • Create one *_twin_current and one *_twin_metrics_timeseries table per twin.
  • Use one shared events table instead of separate per-twin event tables.
  • Keep network / relationship objects as views first; materialize them later only when performance or governance requires it.

2KPI semantic layer

Derive supply-chain KPIs from digital twins, not raw source tables.

  • Create kpi_current and kpi_timeseries.
  • Cover demand, procurement, inventory, production, and distribution KPIs.
  • Standardize definitions, thresholds, and dimensions.

3Control tower

Build the dashboard and natural-language exploration layer once digital twins and KPIs are stable.

  • Pages: executive overview, demand, inventory, procurement, production, fulfillment.
  • Add dedicated digital twin views where users can inspect the current state, history, dependencies, and risk signals for each network twin.
  • Interactive twin-network graph: render the twins as one typed graph (nodes = materials, suppliers, plants, work centres, channels, customers/regions; edges = supplies, BOM, produced-at, routed-through, ships-to), colored by twin risk. Users click any node to drill into its operational data. Delivered in the Twin Explorer app via streamlit-agraph, backed by a v_network_nodes / v_network_edges relationship layer — a material-centric ego graph plus toggleable domain networks (procurement, production, distribution, BOM).
  • Reuse existing Genie spaces.
  • Show current risk, root cause, impacted orders/materials, and recommended next step.

4Alerts and event detection

Create a unified event table for operational abnormalities and plan deviations.

  • Create events.
  • Detect stockout risk, supplier lateness, bottleneck overload, OTIF risk, demand surge.
  • Route alerts by function, owner, severity, and status.

5Planning engines

Add the planning logic that turns state into recommended plans.

  • Inventory policy engine: safety stock, reorder points, coverage targets.
  • MRP engine: demand netting, BOM explosion, planned POs / production orders.
  • Production scheduler and distribution planner after missing master data is modeled.

6Plan-of-record and scenarios

Store committed plans and what-if versions in a governed operational state store.

  • Use Lakebase for operational plan state, mirrored to Delta for analytics.
  • Lifecycle: draft, simulated, recommended, approved, committed, monitored, superseded.
  • Keep approval, rollback, and scenario comparison history.

7Agentic orchestration

Introduce agents only after state, KPIs, events, and plan store exist.

  • Agents diagnose, explain, recommend, simulate, and request approval.
  • Use narrow governed tools, not direct table mutations.
  • Log every tool call, recommendation, approval, and committed action.

5Data Structure Decision

Keep the five business twins separate for clarity, but avoid over-materializing relationship tables too early.

Chosen pattern

Digital twins are separate Delta tables in Unity Catalog. Each twin owns its domain state and history. Shared relationships such as network nodes, network edges, BOM links, supplier-material links, customer-material links, and routing links should start as views over gold_opus5 or modeled reference data. Promote a view to a physical table only when it becomes slow, heavily reused, manually curated, or part of a stable system API.

Five twin current-state tablesMaterialized Delta tablesBusiness-facing state, queried constantly by dashboards, alerts, agents, and planning jobs.
Five twin time-series tablesMaterialized Delta tablesNeeded for trends, anomaly detection, plan-vs-actual, forecast quality, and root-cause analysis.
Network nodes / edgesViews firstAvoid creating and maintaining a graph model until a concrete planning or UI use case requires it.
BOM / supplier / customer / routing relationship objectsViews first; materialize selectivelyMuch of this can be retrieved from gold_opus5; only physicalize when semantics stabilize or performance demands it.
Supply-chain eventsOne shared Delta tableAgents and alerting need one inbox across all twins, not five separate event models.
Plan versions, approvals, comments, overrides, agent action stateLakebase + Delta mirrorMutable operational workflow state belongs in Lakebase; analytics and audit copies belong in Delta.

7Agent Guardrails

These controls make the system agentic rather than prematurely autonomous.

Human approval by default

Agents can recommend and prepare actions, but planner approval is required before committing a plan, changing schedules, expediting POs, or sending supplier/customer communications.

Evidence-backed decisions

Every recommendation must cite the KPI deviation, impacted material/order/customer, root cause hypothesis, scenario comparison, and expected cost/service impact.

Fail-safe behavior

If data is stale, policy parameters are missing, a solver fails, or confidence is low, the agent stops at diagnosis and escalation rather than inventing or executing a plan.

Bottom Line

This design is feasible and realistic as a phased POC. The first deliverable should not be an agent or dashboard. It should be the digital twin state layer, starting with inventory and demand, because that creates the durable state model everything else can trust.
